# 端到端加密技术笔记

写给没接触过密码学的人。先讲概念，再讲这个仓库是怎么做的，最后讲网页和安卓 App 的区别、能防什么、不能防什么。

> 对应的代码：`web/js/crypto.js`（加密本身）、`web/js/sync.js`（什么时候加密、解密）、`server/app.py`（服务器怎么配合）。
> 面向用户的简短说明在 [FEATURES.md](FEATURES.md) 的「端到端加密」一节。

## 1. 先把概念讲清楚

### 1.1 什么是「端到端加密」

日记从你的手机传到服务器，再从服务器传到电脑。普通的 HTTPS 只保护**路上**：网线被人监听也看不到内容，但内容到了服务器，服务器是能读的明文。

端到端加密（E2EE）是：**内容在你的设备上就先锁好，服务器自始至终只拿到锁住的东西，没有钥匙。** 钥匙只在你自己的设备上。「端」指的就是你的各台设备。

```
没有 E2EE：  手机 ──HTTPS──▶ 服务器（明文，能读）──HTTPS──▶ 电脑
有 E2EE：    手机（加密）──▶ 服务器（只有密文）──▶ 电脑（解密）
```

好处：服务器被黑、服务器主人好奇、云厂商被要求交数据，拿到的都只是一堆乱码。

### 1.2 几个必须知道的零件

| 名词 | 是什么 | 在本项目里 |
|---|---|---|
| **对称加密** | 加密和解密用同一把钥匙，像一把既能锁门又能开门的钥匙 | AES-256-GCM |
| **密钥** | 一串随机数，谁有它谁就能解密 | 32 字节（256 位）随机数 |
| **IV（初始向量）** | 每次加密时随机生成的一小段数，保证同样的内容每次加出来的密文都不一样。不用保密，但不能重复 | 12 字节，随密文一起存 |
| **GCM** | AES 的一种工作模式，除了加密，还带一个**认证标签**：密文被改过一个字节，解密就直接失败，而不是解出一堆错的东西 | 提供「防篡改」 |
| **AAD（附加认证数据）** | 不加密、但参与认证的一段信息，解密时必须一致 | 周号，如 `2026-W42` |
| **哈希（SHA-256）** | 把任意内容变成固定长度的指纹，不可逆 | 用来做密钥指纹和版本号 |
| **base32** | 把二进制数据写成字母和数字的一种方式 | 把密钥写成人能抄下来的恢复码 |
| **WebCrypto** | 浏览器自带的密码学接口（`crypto.subtle`），比自己写密码学代码安全得多 | 全部加密都用它，没有第三方库 |

一个常识：**密码学里不要自己发明算法。** 本项目只是把 WebCrypto 里现成的 AES-256-GCM 拼起来用。

## 2. 这个项目想防什么

| 想防的情况 | 能防吗 |
|---|---|
| VPS 被入侵，`data/` 被人拷走 | 能，拿到的只是密文 |
| 服务器主人（你自己或帮你维护的人）偷看熟人的日记 | 能（熟人自己开加密的话） |
| 有人把服务器上 A 周的密文挪到 B 周去冒充 | 能，周号是 AAD，解密会失败 |
| 有人悄悄改了服务器上的密文 | 能，GCM 的认证标签会让解密失败，设备会提示「解不开」 |
| 一台还没装密钥的设备把明文传上来 | 能，服务器直接拒收明文（HTTP 422） |
| **恢复码丢了、所有设备也丢了** | **不能，数据找不回来** |
| 你的手机或电脑本身被入侵 | 不能，设备上本来就有明文 |
| 用网页版时，服务器被改成发恶意页面 | 不能，见第 6 节 |
| 服务器把某一周回滚成旧的密文，或者删掉 | 不能，旧密文也是合法密文 |

## 3. 密钥的一生

### 3.1 生成

在你点「开启加密」时，**浏览器或 App 在本机**用 `crypto.getRandomValues` 生成 32 个随机字节。这就是密钥。服务器没有参与，也从来没见过它。

### 3.2 恢复码就是密钥本身

密钥是 32 个字节，人没法抄。所以把它写成 base32：

- 256 位 ÷ 每个字符 5 位 = 52 个字符（多出的几位补 0）。
- 再加 2 个字符的**校验**（取密钥的 SHA-256 前 2 字节，写成 base32 再取 2 位）。抄错一个字，校验不对，页面会提示，不会装进一把错的密钥。
- 一共 54 个字符，每 4 个一组加横线，方便看。
- 字母表去掉了容易看混的 `I`、`L`、`O`、`U`；输入时 `O` 会当成 `0`，`I` 和 `L` 会当成 `1`。

没有「密码派生」这一步：不是「密码 → 密钥」，**恢复码就是密钥**。所以它必须是随机的，不能自己编一个容易记的。

### 3.3 存在哪

| 地方 | 存什么 |
|---|---|
| 设备（浏览器 `localStorage` 的 `myweek-e2ee-key`） | 密钥，base64 写法 |
| 服务器（`.meta.json`） | 只有 `{"e2ee": true, "keyId": "fa58364c"}` |
| 你的密码管理器 / 纸 | 恢复码，**这是你自己要保管的** |

`keyId`（密钥指纹）= SHA-256(密钥) 的前 4 字节。它的用途只是**认出「这是不是同一把钥匙」**：设备对照服务器上的指纹，就知道自己装的密钥对不对。从 4 字节指纹反推出 256 位密钥是不可能的。

### 3.4 新设备怎么拿到密钥

服务器没有密钥，没法「同步」给新设备。唯一的办法：你在新设备上手动输入恢复码。流程是：填好服务器地址和令牌 → 页面检查 `/api/meta` 发现账号开了加密、本机没密钥 → 提示输入恢复码 → 校验通过且指纹和服务器一致 → 装入。

## 4. 一份日记是怎么被加密的

每一周是一个 Markdown 文本。加密这一周的过程（`crypto.js` 的 `encrypt`）：

1. 随机生成 12 字节 IV。
2. 用 AES-256-GCM，以密钥加密整周文本，**把周号（如 `2026-W42`）作为 AAD**。得到密文和认证标签。
3. 把「IV + 密文」拼起来写成 base64。
4. 前面加一行标记，写成一个文本文件：

```
MYWEEK-E2EE/1 fa58364c
Q2xhdWRlIGlzIHRoZSBiZXN0Li4u...（base64：12 字节 IV ＋ 密文 ＋ 认证标签）
```

- 第一行 `MYWEEK-E2EE/1` 是版本标记，`fa58364c` 是密钥指纹。
- 服务器靠第一行前缀判断「这是密文」，不靠解开它。
- 每次加密都用新的随机 IV，所以同一周内容没变也不一定每次密文都一样，但服务器会判断「内容相同就不写」（见 5.3）。

解密（`decrypt`）反过来：先检查指纹是不是自己这把钥匙，再拆出 IV，用同样的周号作 AAD 解密。任何一步不对（钥匙错、密文被改、被挪到别的周）都会报错，不会解出错的内容。

**加密的粒度是「每周一个文件」。** 文件名（`2026-W42.md`）、文件大小、修改时间，服务器都看得到；看不到的是里面写了什么。

## 5. 同步和服务器是怎么配合的

### 5.1 同步的基本机制（没有加密时就是这样）

每台设备给每一周记两样东西（存在 `localStorage` 的 `myweek-sync:<周号>`）：

- `base`：上次和服务器对上时的版本号（服务器文件内容的哈希）。
- `dirty`：之后本地有没有改过。

规则：本地没改、服务器版本变了 → 拉下来；本地改过 → 带着 `base` 推上去；服务器发现 `base` 过时（有别的设备先改了）→ 回 409，设备把「上次对齐的全文（本地另存的 `myweek-base:<周号>`）、本地、服务器」按条目三方合并（`web/js/merge.js`）后再推。同一条被两边改成不同的字时以服务器为准，本地那条丢掉并提示。不再有冲突副本。

触发时机：每 30 秒、切回页面、恢复联网、本地保存后 2 秒。

### 5.2 加密怎么嵌进去

加密只发生在两个位置，同步逻辑本身没变（`sync.js`）：

- **推送**：账号开了加密，先 `E2EE.encrypt` 再上传。
- **拉取**：下来的内容如果以 `MYWEEK-E2EE/1 ` 开头，先解密，再交给页面。

冲突合并也是在设备上解密之后做的，服务器全程只经手密文。

### 5.3 服务器做了什么（`server/app.py`）

服务器不会加密、也不会解密，它只做规矩上的把关：

| 动作 | 说明 |
|---|---|
| 记录账号设置 | 账号目录下的 `.meta.json`：`{"e2ee": true, "keyId": "…"}` |
| 开启时 | 删掉这个账号 `.history/` 里所有旧明文 |
| 拒收明文 | 账号开了加密后，上传内容不以 `MYWEEK-E2EE/1 ` 开头就回 **422** |
| 不让换密钥 | 已经开了加密，另一把不同指纹的密钥想改设置，回 **409** |
| 历史版本 | 开了加密后，被覆盖的旧明文不再进 `.history/` |
| 版本号 | 对「文件内容」（密文）做哈希。服务器也靠它判断「内容有没有变」 |

### 5.4 开启加密的完整过程

1. 在第一台设备点「开启端到端加密」。页面生成一把新密钥，显示恢复码，**先不装入**。
2. 你保存好恢复码，勾选确认，点「开启加密」，密钥才存进设备。
3. 下一轮同步开始时（`checkAccount`），设备发现「我有密钥，但账号还没开加密」，于是 `PUT /api/meta` 替账号开启，并把**所有周标成待推送**。
4. 逐周推送：这一次推上去的是密文，覆盖服务器上的明文。
5. 其他设备：同步时发现账号开了加密、本机没密钥，提示输入恢复码。

```
设备A（有钥匙）                          服务器                         设备B（新）
  生成密钥 → 显示恢复码
  PUT /api/meta {e2ee, keyId} ────────▶ 写 .meta.json，删旧明文历史
  逐周 加密 → PUT /api/weeks/… ───────▶ 检查是密文 → 存下
                                                    ◀── GET /api/meta ──── 发现开了加密
                                                         提示输入恢复码
                                                         校验指纹对 → 装入密钥
                                        ── 密文 ──────────────────────────▶ 解密显示
```

## 6. 网页版和安卓 App 的区别

**用的是同一套代码**（`web/js/`），加密原理完全一样，密文格式也一样，所以网页和 App 可以互通。区别在「代码从哪来」和「钥匙放哪」：

| | 网页版（https://week.fugueh.top） | 安卓 App（APK） |
|---|---|---|
| 页面代码来自 | **服务器**，每次打开从服务器取 | **打包在 APK 里**，安装后不变 |
| 加密实现 | 浏览器的 WebCrypto | App 内置 WebView 的 WebCrypto |
| 密钥存放 | 这个浏览器、这个网站的 `localStorage` | App 的 WebView 的 `localStorage`，在 App 私有目录里，别的 App 读不到 |
| 和网页互通吗 | 互通：输入同一个恢复码就是同一把钥匙 | 同左，**但钥匙各存各的**，不会自动共享 |
| 清缓存 / 卸载 | 清站点数据会丢密钥（要重输恢复码） | 卸载 App 或清数据会丢密钥 |
| 本地文件夹 | Chrome / Edge 可连一个文件夹 | 通过原生插件 `FolderStorePlugin.java`，用系统文件夹选择器 |
| 缓存 | 有 Service Worker（`sw.js`），旧页面可能多留一次 | 不走网页缓存，装新版就是新代码 |
| 环境要求 | 必须 HTTPS（WebCrypto 只在安全环境下可用） | WebView 里默认就满足 |

### 6.1 为什么说 App 的信任更少

网页版的流程是：你打开网址 → **服务器发给你** HTML 和 JS → 浏览器执行。如果服务器想作恶，它可以悄悄把页面换成一个「把你的密钥偷偷传回来」的版本，E2EE 就形同虚设。也就是说，**网页版里你仍然要信任服务器给你的页面代码。**

App 的代码在你安装时就固定了（并且是从公开仓库用 GitHub Actions 构建的），之后服务器只能给它数据，改不了它的程序。所以抵御「恶意服务器」时，App 更强。

对你自己用，影响不大（你就是服务器主人）；对熟人，这是一个值得知道的差别。

### 6.2 两个容易误会的点

- **本地文件是明文。** E2EE 保护的是「服务器上的那份」。设备里的 `localStorage`、你连的本地文件夹里的 `.md`，仍然是明文，这是设计如此（方便你用任何编辑器改）。
- **本地文件夹是 App 的明文备份。** 所以恢复码丢了而本地文件夹还在，数据就还在。这也是文档里说「本地文件夹里的明文文件不受影响」的原因。

## 7. 安全上的几个取舍（诚实地写出来）

1. **没有密码派生（KDF）。** 恢复码就是密钥本身，足够随机（256 位），所以不需要。代价是：你不能自己选一个好记的短密码。
2. **随机 IV 的上限。** 12 字节随机 IV 配 AES-GCM，同一把密钥加密次数远低于 2³² 次是安全的。一个人写日记不会逼近这个数。
3. **密钥存在 `localStorage` 里，没有进 Android Keystore。** 在同一个 WebView 里的脚本能读到它。对个人手帐够用；如果设备被 root 或被恶意软件控制，就保护不了。
4. **元数据会泄露。** 服务器能看到：有哪几周、每周的大小、什么时候改的、账号是否加密、密钥指纹。
5. **不防回滚和删除。** 服务器如果把某周换成它保存的旧密文，设备分辨不出（旧密文也是合法的）。
6. **不支持关闭加密。** 真要关，流程是：导出所有周 → 服务器上删掉该账号的 `.md` 和 `.meta.json` → 清掉设备本地存储 → 重新导入并同步（见私人备忘 `NOTES.md`）。
7. **服务器上的明文历史在开启时被删。** 但如果服务器所在的磁盘做过快照或备份，快照里可能还留着旧明文，这是服务器之外的事。

## 8. 怎么自己检查它是不是真的加密了

在服务器上看账号目录：

```bash
cat ~/my-week/data/.meta.json              # 看 e2ee 是不是 true、keyId 是多少
head -c 60 ~/my-week/data/2026-W42.md      # 加密后应该以 MYWEEK-E2EE/1 开头
```

- 开头是 `MYWEEK-E2EE/1 <8 位指纹>`，后面是乱码一样的 base64：已加密。
- 开头是 `---` 和 `week: …`：还是明文，**没有被换成密文**。

## 9. 已修复的疑点：服务器上是明文却被当成「已一致」

开启加密后，设备应该把服务器上所有周重新加密上传。但实际检查时，服务器上的 `2026-W42.md` 一度在开启加密之后仍然是明文。

原因（读代码得到的推断，已用测试覆盖）：旧的 `push()` 遇到 409 时，如果解出来的服务器内容和本地内容「相同」，就把这周标成已同步并返回，没有再推密文。服务器上是明文时，这样会让明文一直留着。

现在的处理：服务器版本是明文、而账号已开加密时，不把「内容相同」当作已同步，仍然把密文推上去（`tests/sync.test.js` 里有对应的测试，旧代码跑不过它）。

## 10. 名词小抄

| 词 | 一句话 |
|---|---|
| 明文 / 密文 | 能直接读的内容 / 加密后的乱码 |
| 对称加密 | 加密解密用同一把钥匙 |
| AES-256-GCM | 一种对称加密算法（256 位密钥）加上防篡改认证 |
| IV | 每次加密随机生成的一小段数，不保密，不能重复 |
| AAD | 不加密、但必须一致才能解开的附加信息，这里是周号 |
| 哈希 | 把内容变成固定长度指纹，不可逆 |
| 密钥指纹（keyId） | 密钥哈希的前 4 字节，用来认钥匙，不能还原钥匙 |
| 恢复码 | 密钥本身写成 54 个字符的样子，用来把密钥带到新设备 |
| WebCrypto | 浏览器自带的密码学接口 |
| 端到端加密 | 钥匙只在你的设备上，服务器只有密文 |
| HTTPS | 保护传输路上的内容，和 E2EE 是两层不同的保护 |
