# 离线与在线：用户体验说明（供评审）

这份文档描述「我的一周」在**没网、有网、网络不稳**时，用户实际会遇到什么，以及背后的取舍。写给要来挑毛病的人：我把已知的弱点单独列出来了，没有验证过的地方也标明了。

对应版本：`v0.2.2`。代码在 `web/js/`（`store.js` 本地存储、`sync.js` 同步、`merge.js` 合并、`crypto.js` 端到端加密），测试在 `tests/`。

## 1. 先说结论

- **设计取向是「本地优先」**：每台设备本地都有完整数据，写的时候永远先写本地，不等服务器。没网也能记。
- **服务器不是实时的唯一真相，而是各设备最终汇合的地方。** 联网后自动同步，两边都改过就按条目合并。
- 我们**没有**采用「联网用户本地只读、服务器是唯一标准」的设计（讨论过，见第 8 节），因为日记是随手记的东西，没网时记不了的代价太大。
- 冲突时的规则很简单：**不同条目都留下；同一条被两边同时改成不同的字，后推送到服务器的那一边为准。**

## 2. 三种使用方式

| 方式 | 谁在用 | 数据在哪 | 离线 / 在线的区别 |
|---|---|---|---|
| **纯本地** | 没填令牌的人 | 只在本机（浏览器 localStorage，或连了本地文件夹） | 不存在离线问题，也没有同步和冲突 |
| **联网同步** | 填了服务器地址和令牌 | 本机一份 + 服务器一份，自动保持一致 | 本文重点 |
| **联网同步 + 端到端加密** | 在「同步」里开了加密 | 同上，但服务器上是密文 | 多一个「密钥在不在本机」的条件，见第 6 节 |

同一套页面代码跑在两处：网页（https://week.fugueh.top，可添加到主屏幕）和安卓 App（页面打包在 APK 里）。

## 3. 一次修改，从敲键盘到上服务器

```
敲字 ──▶ 本地保存（约 0.6 秒后）──▶ 同步（再过约 2 秒）──▶ 服务器
        写进 localStorage          带着「我基于哪个版本」PUT
        并标记这一周「待推送」        成功 → 记下新版本
                                    409（别人先改了）→ 合并后再推
```

- 没有「保存」按钮，也没有保存提示以外的操作。
- 同步另有触发：每 30 秒一次、切回页面（0.3 秒内）、恢复联网（0.3 秒内）、切到后台或关页面时（先把还在 0.6 秒等待里的字立刻写进本机，再推一次）。
- 每个请求最多等 15 秒，超时算失败，下一轮照常重试。
- 页面标题旁的小胶囊显示状态：绿色「已同步 HH:MM」、灰色「N 周待上传」、黄色「有提醒」、红色「同步出错」、灰色「离线中」或「离线 · N 周待上传」。**只要还有没上传的改动，就不会显示绿色的「已同步」。**

**页面本身怎么更新（网页版）：** 页面文件（`index.html`、css、各个 js、图标）由 Service Worker 整版缓存，打开时全部从这一版里取，不等网络，没网也能开。
- 新版本只能整版换：服务器上的 `sw.js` 变了 → 浏览器在后台把新版的全部文件一次下好（任何一个失败就整版作废，继续用旧版）→ 新版先等着。运行中不会再逐个文件写回缓存，所以不会出现新 `app.js` 配旧 `sync.js`。
- 新版下好后，页面底部出现「有新版本，点这里刷新」；点了先把 0.6 秒等待里的字写进本机，再切换并刷新。没点的话，下次打开或切回页面时，只要没在输入框里打字、也没有等待中的保存，就自动切过去刷新一次（切换用的是已经下好的文件，不用等网络）。
- 所以部署后的第一次打开还是完整的旧版，第二次打开（或点提示）是完整的新版。
- 版本号是 `sw.js` 里 `CACHE` 名后面的哈希，按这些文件的内容算。改了 `web/` 下的页面文件要跑 `npm run bump-sw`；忘了的话 `npm test` 里的 `tests/sw-version.test.js` 会失败。
- App 版页面在 APK 里，不用 Service Worker，随 App 更新。

## 4. 场景逐个看

### 4.1 完全没网（地铁、电梯、飞行模式）

| 想做的事 | 结果 |
|---|---|
| 打开页面 | 网页版用 Service Worker 缓存打开，App 版页面本来就在 APK 里。可以打开 |
| 看已有的周 | 可以，读的是本地数据 |
| 写日记、加事项、勾选目标 | 可以，立即写进本地，这一周被标成「待推送」 |
| 同步 | 不尝试，胶囊显示「离线中，联网后自动同步」 |
| 联网后 | 0.3 秒内自动同步，用户不需要操作 |

**限制：** 一周里没同步过的新设备，没网时没有数据可看（本地是空的）。

### 4.2 有网，只有一台设备在用

最简单的情形：改完约 2.6 秒后服务器就有了，之后每 30 秒、切回页面时再对一次。用户看到的就是「已同步」。

### 4.3 有网，两台设备在不同时间用

A 写完 → 自动上传。B 之后打开或切回页面 → 在 0.3 秒内拉取，页面刷新成 A 写的内容。

**一个有意为之的细节：** B 的页面如果**正在输入**，或者本地这一周有没推完的改动，同步时会**跳过拉取**，免得把用户打到一半的字刷掉。所以 B 看不到 A 的新改动，要等 B 写完推送之后才会合并。

### 4.4 两台设备在同一段时间内改了同一周

触发条件：B 推送时带的「基于哪个版本」已经过时，服务器回 409。设备于是做**条目三方合并**，用三份东西：上次对齐的全文（base，本地另存）、本设备现在的、服务器现在的。

| 情形 | 结果 |
|---|---|
| 两边各加了不同的条目（包括日记顶部各插一条） | 都留下 |
| 只有一边删了某条 | 删掉 |
| 只有一边改了某条的字 | 用改后的 |
| **同一条被两边改成不同的字** | **后推送的一边为准**，先到服务器的那一版被覆盖；后推送的这台设备会提示被替换的是哪几条（胶囊变黄，一直留到用户点开胶囊看过），没有「冲突副本」 |
| 合并本身出错（比如某一边读不懂） | 本地内容原样保留、继续待上传，这一周报错（胶囊变红），其他周照常同步 |
| 一边拖动了顺序 | 本设备调整过就用本设备的，否则用服务器的 |
| 勾选状态、复盘 | 本设备改了就用本设备的，否则用服务器的 |

**用户视角：** 绝大多数情况下什么都不会发现，两边的内容自动合在一起。只有「同时改了同一条」才会有一边被覆盖，后推送的那台会看到提示；先推送的那台不会收到提示，旧版留在服务器 `.history/`。

### 4.5 一台设备离线很久，回来同步

- 离线期间的所有本地改动都在，联网后和服务器合并。
- 合并依据的是「上次对齐的全文」，所以「谁删了什么」能分得清，不会把对方删掉的条目带回来。
- 如果这周在服务器上被别的设备大改，合并是按条目做的，**不是按时间**；设备时钟不参与任何判断。

### 4.6 新设备第一次同步（没有 base）

这时没有「上次对齐的全文」，合并只能做**并集**：不传播删除。意思是：如果新设备本地原来就有这一周的旧内容，而服务器上这些条目已被别人删掉，它们可能被带回来。之后每次同步都会保存 base，就恢复正常。

### 4.7 网络不稳（能连但经常被重置）

- 单次同步失败 → 胶囊变红，写明原因，30 秒后自动重试。
- 连上了但请求一直不返回（弱网、需要网页登录的 Wi‑Fi）→ 15 秒后算失败，不会一直卡着；这期间胶囊显示「N 周待上传」，不会是绿色。
- 本地数据不受影响，随时可以继续写。
- 我们在开发时就遇到过从国内连 GitHub 被重置；服务器在东京，同类问题可能出现，但还没有量化过成功率和延迟。

## 5. 数据放在哪，哪些情况会丢

| 位置 | 内容 | 什么时候没了 |
|---|---|---|
| 浏览器 / WebView 的 localStorage | 每周全文、同步状态、base、加密密钥 | 清站点数据、换浏览器、无痕窗口、**卸载 App** |
| 服务器 `data/` | 每周一份（可能是密文） | 服务器出问题。服务器上的 `.history/` 会保留每次被覆盖前的旧版（加密账号保留的是旧密文，开启加密那一刻之前的明文历史已被删） |
| 本地数据文件夹（可选） | 每周一个明文 `.md` | 用户自己删 |
| 本机快照（IndexedDB） | 每周最近 30 份旧版本（拉取、合并、文件夹读回、导入、恢复之前各存一份；自己编辑每 10 分钟最多一份；合并时被替换的另一台的版本也存一份） | 同 localStorage：清站点数据、卸载 App |
| 本机同步记录（localStorage） | 最近 200 条上传、下载、合并、出错记录 | 同上；也可以在面板里清空 |

**会真的丢数据的情形：**

1. **离线写了东西，还没联网同步，就清了数据或卸载了 App。** 那部分只存在本地，找不回来。
2. 开了加密的账号，**所有设备都丢了而恢复码也丢了**，服务器上的密文再也解不开。
3. 同一条被两边同时改，先推送的那一版被覆盖（这是设计内的行为；后推送的一边会看到提示，旧版在服务器 `.history/` 里）。

能找回的：本机内容被同步、合并、文件夹或导入换掉之前都有快照，在「历史版本」里可以预览和恢复（恢复算一次本地编辑，会同步到其他设备）。同一条被两边改时，被替换的另一台的那一版也存成了快照。

已经堵上的：合并出错时以前会整份换成服务器的版本、悄悄丢掉本地改动，现在改成保留本地并报错；最后 0.6 秒内打的字以前在关页面时可能没写进去，现在关页面和切后台时会立刻写入。
4. 浏览器存储满了写不进去，页面会提示，但不会自动清理。

## 6. 端到端加密怎么影响离线 / 在线

- 密钥只存在设备本地。**离线写、离线读都不受影响**：本地存的是明文，加密发生在推送时、解密发生在拉取时。
- **新设备要读加密账号的数据，必须先联网**：要填令牌，页面向服务器确认账号开了加密，再输入恢复码。离线时做不到。
- 开了加密的账号，服务器拒收明文。如果某台设备上没有密钥、又有未推送的改动，同步会报错，改动停在本地。
- 服务器上看到的只有密文、每周的大小和修改时间。

## 7. 已知的弱点（欢迎直接挑）

| 弱点 | 影响 | 现状 |
|---|---|---|
| **粒度是「整周一个文件」**，每次推送都是整份覆盖 | 两台设备同时在线编辑同一周，冲突概率比按条目存储的方案高；全靠合并兜底 | 合并按条目做，测试覆盖了常见情形，但没有真实多设备长期使用的数据 |
| **同一条被同时改时，先推送的一方没有提示** | 先推送的那台会奇怪「我刚才改的那条怎么变了」 | 后推送的一方已有提示；先推送的一方要等有了版本历史界面才好提示 |
| **历史版本只有本机快照** | 「历史版本」能恢复这台设备上存过的旧版；但在别的设备上写、这台从没拉到过的版本不在里面。服务器 `.history/` 里有全部被覆盖的旧版，页面上还没有入口 | 先做了本机这一层；服务器历史的入口以后再加 |
| **第一次同步没有 base，只做并集** | 极少数情况下被删的条目会复活 | 只发生在新设备首次同步 |
| **手机后台时同步会推迟** | 安卓 WebView 在后台时定时器可能被暂停，写完立刻切走、同步可能要等下次打开 | 没有在真机上验证过 |
| **待上传只精确到「周」** | 胶囊显示「N 周待上传」，不是「N 条」 | 足够判断「有没有东西还没上去」 |
| **页面不跟踪另一台设备的实时输入** | 只有同步时才更新，不是协同编辑 | 不是目标 |
| **服务器可以回滚或删除某周的密文，设备发现不了** | 对服务器的信任仍然存在 | E2EE 不防这个 |
| **网页版的页面代码来自服务器** | 恶意服务器可以改页面截走恢复码 | App 版不受影响；已写进文档 |

## 8. 讨论过但没有采用的设计

**「联网用户本地只读，服务器是唯一标准」：**

- 优点：没有冲突，用户看到的永远就是服务器上的；同步代码大幅简化。
- 缺点：没网不能写，每次修改都要等服务器确认；国内访问东京服务器偶尔会被重置，写日记时失败体验很差；还要处理「第一次开启同步时本地已有的数据怎么办」。
- 最终没有采用，原因是日记场景下「随时能记」比「永远没有冲突」更重要，同时两三个人用，同一条被同时改的概率极低。

**文本行级三方合并（diff3）：** 日记新条目写在列表最上面，两边各在顶部插一条会被判成冲突，所以改成了按条目合并。

**CRDT / OT（Google Docs、Apple Notes 一类）：** 对一个个人项目太重。

## 9. 测试到什么程度

- `npm test` 跑 32 项：18 项合并规则（两边各加、删、改、拖动、勾选、复盘、无 base、幂等），14 项同步（用内存里的假服务器和两台假设备，包括合并出错、请求超时、待上传计数、关页面前写入、快照、恢复、同步记录）。快照在测试里用内存后端，IndexedDB 那一层只在浏览器里手动验过。
- **没有做的：** 胶囊各状态在真实页面上的显示、真机（安卓）上的离线 / 恢复联网流程、手机切后台后的同步、多天离线后的合并、真实网络下的延迟和重试、浏览器存储满了的情形、多个用户并发。
- 同步和加密的结论多数来自读代码和测试，不是线上长期运行得出的。

## 10. 想请评审重点看的问题

1. 「同一条同时改，后推送的为准，且不提示」是否合理？是否应该至少给被覆盖的一方一句提示？
2. 整周一个文件、整份覆盖的存储粒度，是否会在实际使用中带来问题？值不值得改成每条一份或操作日志？
3. 离线时只显示「离线中」，没有待同步数量，是否影响用户的安全感？
4. 清除数据、卸载 App 会丢掉未同步的离线内容，应该怎么提醒？是否该在卸载前（或定期）自动导出？
5. 新设备首次同步没有 base，只做并集的处理，是否有更稳妥的办法（比如让用户选「以服务器为准」或「合并」）？
6. 加密账号下，新设备必须联网并输入恢复码才能读数据，这个流程是否足够清楚？恢复码丢失的风险有没有更好的缓解方式？
7. 安卓后台时同步被推迟，要不要用系统的后台任务（WorkManager）做可靠同步？值不值得为这个增加原生代码？
8. 整体上，「本地优先 + 合并」对这个项目的规模是不是过度设计？有没有更简单、更不容易出错的方案？
